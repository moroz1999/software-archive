# Import from vektor-06c.ru

A backend command that takes the software of vektor-06c.ru into the archive ([domain/imports.md](../domain/imports.md)). Only the reading of the site and the conducting of the run are its own: `VektorSourcePrograms` turns each program of the site into what [the one import](imports.md) takes in, by the rules of the site.

## Running

- An administrator starts it on the Imports tab of management (`/management/imports`, `features/import/source`), choosing the source vektor-06c.ru: the whole site, or one section chosen by the code in its address. The sections offered are those the import places in categories, so the list is kept in one place, `VektorSections`. Production runs it once on an empty archive, whole; locally a small section is enough to try it.
- The tab says the import has started, or why it could not: another run is going on, or the user is not an administrator.
- Below the form, the report of the run started last: what it imports, its state (running, done, stopped), when it ran, the counts and, while it runs, the program it is at, leading to its page on the site. Then its log, one line per step with its time: each page of the list read, leading to it; each file downloaded; what each program came to — added or already there leading to its software (one deleted since named without a link), left out leading to its page on the site, failed with the page and the reason; each author taken, leading to its page; each place added. While the run goes on the tab reads the report again every 5 seconds, asking only for the lines after the last one it has (`after`) and adding them below.
- A run takes far longer than a request waits, so it goes to the application's pool of background threads (`applicationTaskExecutor`, not the scheduler of the search worker) and the request is answered at once. Only one import runs at a time, of any source ([imports.md](imports.md#running)); restarting the backend stops a run, and the next run takes up what is left.
- Every run is an `ImportRun` (`import_run`, `V21`), written down before it starts so that its report fills from the background thread. Its log is `import_run_log` (`V36`): lines are only appended, a `bigserial` `seq` orders the lines of every run, and what a line tells is JSON of its kind. A run read back holds no lines; the ones logged since are appended by the repository on save (`pullNewLog`). A page of the list read and the files of a program downloaded are logged as they happen (`RecordImportLogHandler`), each in a transaction of its own; what a program came to, with the authors and places it took (`CreditImportedAuthorsHandler`) and what was added to software found (`SupplementSoftwareHandler`), is logged in the transaction that takes it in, so a program that fails leaves none of them, only its downloads and its failure. Before each program the run writes which one it is at (`RecordImportProgressHandler`); the site lists its programs page by page, so no total is known. `V36` carried the reports of runs before it (`import_run_added`, `_known`, `_skipped`, `_failed`, `_author`, `_place`, `V33`) into their logs, part after part, without a time; those tables keep them. A found program counts as known: the software the archive already has, by origin or by its program files. The run ends done; a failure of the whole run ends it stopped, and so does a restart: on start the application stops every run still marked running. The log of the application keeps the summary and every failure with its cause. What a run added reaches the search through the outbox like any other change.
## REST

| Call | Answer | Errors |
|---|---|---|
| `GET /api/imports/vektor/sections` | `["3d-programmy", …]`: the codes of the sections to choose from, in alphabetical order | `401 auth.required`; `403 access.denied` for anybody but an administrator |
| `GET /api/imports/last-run[?after=<seq>]` | `{run}`: `null` before the first run; else `id`, `archive`, `section` (`null` for the whole site), `state` (`running`, `done`, `stopped`), `startedAt`, `endedAt` (`null` while running), the counts `added`, `known`, `skipped`, `failed`; `progress` `{position, total, url}`: the program it is at, counted from 1, 0 while it reads the list, `total` `null` when unknown; `log` `[{seq, at, kind, entry}]`, all the lines or only those after `after`, in their order: `at` `null` for a line carried over from before the log; `entry` by `kind` — `list` `{url, number, pages, programs}` (`pages` `null` when unknown), `download` `{externalId, title, file, name, size}` (`file` `archive` or `screenshot`), `added` `{externalId, softwareId, title, exists}`, `known` the same with `supplements` (`description`, `release-date`, `preservation`, `categories`, `credits`, `screenshots`), `skipped` `{externalId, url, title, reason, detail}` (`reason` `section` or `category`, `detail` its name in the source), `failed` `{externalId, url, reason}`, `author` `{kind, id, name, created, exists}` (`kind` `author`, `group` or `label`; `created` false for one found in the archive), `place` `{kind, name}` (`city` or `country`) | `401 auth.required`; `403 access.denied` for anybody but an administrator |
| `POST /api/imports/vektor[?section=<code>]` | `202` once the run is started | `401 auth.required`; `403 access.denied` for anybody but an administrator; `409 import.running` while a run goes on |

## Rerunning

- Every program is read again on every run and goes to [the one import](imports.md), which finds the software it became and adds only what it lacks. A program also keeps the address of its page (`url`, `V19`), which the software page links to as its source; the address cannot be built from the id, so it is taken from the list it was found in. An author name is a label remembered by the name itself.
- Deleting software forgets its origin in the same transaction (`SoftwareDeleted`, answered by `importer/app/ForgetDeletedSoftwareHandler`), so the next run adds the program again; `V20` forgot the origins of software deleted before.
- Each program is taken in a transaction of its own: its labels, software, release with the archive, screenshot and origin commit together or not at all, so a failed program leaves no trace and is tried again by the next run. Its archive and picture are downloaded before it, so a failed download fails only that program.
- The importer's account is created by the schema (`V18`); nobody can sign in with it.

## Reading the site

- `VektorSite` is the port the run reads through, a page of the list at a time so that the run logs each as it reads it: the first page gives the addresses of the others as its pagination links them, up to the last page it names — the whole catalog numbers its pages by `PAGEN_2`, a section by `PAGEN_1`. `HttpVektorSite` parses pages with `VektorPages`.
- `JdkSourceHttp`, shared with every source, asks one thing at a time with a pause before each request, growing with every retry; a server failure (5xx, 429) or a broken connection is tried up to three times, a missing page once.
- The archive and the picture are downloaded whole into memory: the site's files are far below the limits of release archives and screenshots.
- The picture the site shows when it has no screenshot (`Skrinshota-net…`) is not taken.
